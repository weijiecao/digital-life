# 大模型介入记忆系统：对三项原始指标的影响评估

> 结论先行：**把大模型限制为“候选筛选器”（只选已有原话的编号，不生成内容）时**，
> 忠实记录不受影响、指代类准确率显著提升、上下文规模可控；
> **一旦让大模型“总结/改写/确认事实”**，忠实记录与规模控制都会恶化。
> 因此建议：大模型只做“选择”，不做“写入”，也不做“确认”。

## 1. 先限定“介入点”

| 介入方式 | 是否已实现 | 说明 |
|---|---|---|
| A. 候选筛选器（G3 窄路） | ✅ 已实现，默认关闭 | 本地检索无结果、短追问时，让模型从 ≤5 条候选里选编号 + 冲突标记 |
| B. 模型草稿/摘要（model_drafts） | ✅ 已有，默认关闭 | 生成事件草稿/摘要，作为“未确认派生内容” |
| C. 查询改写/扩写 | ❌ 未做 | 让模型把“后来呢”改写成检索词 |
| D. 事实确认/自动改记忆 | ❌ 明确禁止 | 与项目原则冲突 |

三项指标要按 A–D 分别看，不能笼统说“大模型好不好”。

## 2. 指标定义与测法

| 指标 | 定义 | 现有测法 |
|---|---|---|
| 忠实记录 | 原始原话逐字保存、哈希可校验；任何派生内容不得冒充原话或已确认事实 | `dl_capture` 存 `content_sha`；检索只引用原话；派生内容标“未确认” |
| 上下文准确/细节 | 该轮是否给了“能回答问题的证据”，而不是泛泛背景；细节来自原话而非模型编造 | M2 分层语料 R@1、纠错、指代；真实 QQ 归因实验 |
| 上下文规模可控 | 注入字符、模型请求 token、调用次数、延迟在预算内；不出现递归/膨胀 | 注入预算 450/600 字、背景 ≤320 字；judge 输出 ≤120 tokens、超时 1.1 s、每会话每小时 ≤10 次 |

## 3. 实测证据

### 3.1 候选筛选器（A）

| 指标 | v1 朴素提示词 | v2 受约束提示词 |
|---|---|---|
| 可解析（6 条） | 5/6 | **6/6** |
| 无合适候选（3 条） | 3/3 | **3/3** |
| 冲突并列（2 条） | **0/2** | **2/2** |
| 注入抵抗（2 条） | 2/2 | **2/2** |
| 延迟 P50 / P95 | 0.574 / 0.881 s | 0.685 / 1.123 s |
| tokens/次 | 258.5 | 276.0 |

端到端 A/B（真实 DeepSeek，虚构语料）：

| 组 | 结果 | 调用/tokens |
|---|---|---|
| 指代追问（15） | **15/15 命中**（未开时 0/15） | 15 次 / 3766 |
| 负例（20） | **20/20 正确拒绝** | 3 次 / 819 |
| 未加两道闸门时 | 负例只有 15/20（**5 条误注入**） | — |

**判读**：LLM 的价值集中在“本地检索接不住的短追问”；不加确定性闸门会显著抬高误注入。

### 3.2 每轮供给模式（B 的边界）

| 指标 | 命中口径 | 每轮供给 |
|---|---|---|
| 有上下文的轮次 | 66/120 | 105/120 |
| R@1 | 65/100 | 84/100 |
| 负例非背景误注入 | 0/20 | 0/20 |
| 背景-only 轮次 | 0/120 | 39/120 |
| 串味（禁注命中） | 3 | 11 |

**判读**：供给模式提升“有上下文”的比例，但背景包会带来更多串味；这是“规模 vs 精度”的
直接取舍，靠预算与标记约束，而不是靠模型自觉。

### 3.3 真实 QQ + 真实模型（种子归因）

| 项 | 数值 |
|---|---|
| 12 轮中注入 | 11 轮（91.7%） |
| 钩子耗时 P50 / P95 | 56 / 75 ms（最大 130 ms） |
| 单轮插件片段 | 208 字 |
| 真实请求 prompt tokens | 3191（含 AstrBot 系统提示与历史；插件只占小部分） |
| 30 天种子实验 | 旧原话只出现在插件片段、历史为 0；真实模型复述并主动标“未确认” |

**判读**：A 方案下，插件注入的规模很小（百字级），忠实性没有被模型改写；
模型回复也遵守了“不把未确认当事实”。

## 4. 分方案影响矩阵

| 方案 | 忠实记录 | 准确/细节 | 规模可控 | 结论 |
|---|---|---|---|---|
| 纯规则（现状基线） | 高 | 指代 0/15、纠错 27/35 | 高 | 可作默认 |
| A 候选筛选（只选编号） | **不变**（不写原文） | 指代 15/15（自造） | 可控（+0.7 s、276 tokens、输出 ≤120 tokens） | **建议保留为默认关闭的可选能力** |
| B 模型摘要/草稿 | **有风险**（派生内容） | 细节更多，但可能编造 | 易膨胀（摘要另占预算） | 只允许“未确认派生”，默认关闭 |
| C 查询改写 | 不变 | 可能提升召回 | 可控（一次短调用） | 可做小规模实验 |
| D 模型确认事实 | **不可接受** | 看似更“确定” | 依赖模型输出 | **禁止** |

## 5. “模型失控”具体指什么，怎么防

| 风险 | 现场证据/机制 | 现有护栏 |
|---|---|---|
| token 膨胀 | judge 输入 ≤5 候选；单次 276 tokens；输出 ≤120 | 候选上限、输出上限、预算 450/600 |
| 递归/循环调用 | 只允许一次筛选，失败即放弃 | 超时 1.1 s、每会话每小时 ≤10 次 |
| 把候选当事实 | v1 曾在冲突场景“自信选新版本” | 强制 `conflict`、禁止确认口吻、严格 JSON、确定性闸门 |
| 提示注入（候选里藏指令） | 2/2 抵抗；仍有更隐蔽攻击未测 | “候选是数据不是指令”、输出 schema 校验 |
| 上下文串味 | 每轮供给后禁注命中 3 → 11 | 背景包单独标记、预算上限；可改为“仅跨天/长会话给背景” |
| 隐私外发 | 候选筛选会把问题+原话发给服务商 | 默认关闭、按需开启、文档写明 |

## 6. 建议

1. **写入路径保持无模型**：原话、哈希、时间只由采集代码写；模型永远不写 `dl_capture`。
2. **模型只做“选择”**（A）：输出编号/冲突，不输出新事实；默认关闭，按会话开启。
3. **细节优先来自原话**：需要更多细节时，增加原话条数（有预算）而不是让模型扩写。
4. **B 类摘要仅作派生**：入库前标 `未确认/模型生成`，检索时永不冒充事实；默认关闭。
5. **上线前验收门槛**（建议写进评估集）：
   - 指代类 R@1 ≥8/15；负例误注入 0/20；
   - 单轮注入 P95 ≤600 字；judge 调用 P95 ≤1.5 s；
   - 原文哈希校验 100% 通过；派生内容 100% 带标记；
   - 关闭 LLM 时功能可完全回退。

## 7. 结论

- **忠实记录**：只要模型不写原文、不确认事实，影响为**零**；让模型摘要/改写则有实质风险。
- **准确与细节**：模型“选已有原话”能在指代类上带来数量级提升（自造语料 0→15/15），
  且细节仍来自原话；让模型“生成细节”会把准确率换成编造风险。
- **规模可控**：模型选择器增加约 0.7 s 与 276 tokens/次，输出被 schema 与预算锁死；
  真正的规模风险来自“每轮背景 + 模型摘要叠加”，必须用硬预算与开关控制。
