# 归因：插件上下文 vs AstrBot 自带上下文

## 1. 为什么难区分

AstrBot 每轮发给模型的请求里本来就有：

- 系统提示（人格/指令）；
- **最近若干轮对话历史**（它自己的上下文机制）。

本插件做的是在同一条 user 消息里**追加一个临时 TextPart**，开头固定为
`[DL_MEMORY_V040]`（或背景包 `背景上下文`）。两者都在 `messages` 里，模型不会告诉你
“这句是插件给的”。所以不能凭“模型答对了”就归因给插件。

## 2. 判据：看信息出现在哪一侧

| 暗号出现位置 | 结论 |
|---|---|
| 只在 `[DL_MEMORY_V040]` / `背景上下文` 片段里 | 这次只能由插件提供 |
| 也出现在普通对话历史里 | AstrBot 自带窗口就能提供，**不能**归因给插件 |
| 两边都没有，模型却答出 | 不是本插件提供（模型幻觉/其他记忆机制） |
| 请求里根本没有插件片段 | 这一轮插件没供给（检查配置/白名单/长度/缺口） |

## 3. 推荐实验：唯一暗号 + 推出窗口

1. 选一个**绝不会出现在系统提示里**的暗号，例如 `蓝鲸7391`。
2. 给小号发：`记住一个暗号：蓝鲸7391`（插件采集；AstrBot 当下也能看到）。
3. 发 **40–60 条无关短消息**（或足够长的内容），把这条挤出 AstrBot 的最近窗口。
4. 问：`我之前让你记的暗号是什么？`
5. 运行归因工具：

```powershell
cd testbed
.\.venv\Scripts\python.exe harness\attribution.py --secret 蓝鲸7391 --since 2026-11-04T12:00:00
```

6. 看模型回复 + 工具输出：
   - 工具显示 `暗号只在插件片段 > 0`，且回复准确说出 `蓝鲸7391` → **插件起作用**；
   - 工具显示 `暗号在普通历史里`，回复也说对 → 可能只是 AstrBot 窗口没滑出去，实验无效；
   - 工具显示两边都没有，回复却说对 → 不是插件（检查是否另有记忆插件/模型幻觉）。

> 关键：如果第 3 步没有把暗号挤出窗口，A/B 或“答对了”都不能证明插件有效。

## 4. 辅助方法

### 4.1 看每轮请求体

```powershell
Get-Content logs\llm_requests.jsonl -Tail 5
```

- 本轮没有 `[DL_MEMORY_V040]` / `背景上下文` → 这轮插件没供上下文；
- 有 → 至少供给发生了，但“模型是否采用”仍要看回复。

### 4.2 关掉插件做对照

`enabled=false`（或只关 `always_context_enabled`）后重发同一段脚本：

- 只适合“暗号已在长程记忆、且已滑出窗口”的情况；
- 否则 AstrBot 自带历史仍然能答对，对照无效。

### 4.3 别用 mock provider 判效果

testbed 的 mock 回复是固定文本，只能证明“注入进入请求体”，不能证明“模型用了”。
要判效果必须走真实模型（QQ 实际对话或真实 provider）。

## 5. 已知干扰

- **背景包**（每轮供给）可能包含较早原话，因此暗号可能出现在“背景上下文”里——
  仍属于插件供给，但不是“相关召回”。若要测相关召回，问题里带上暗号关键词
  （如“暗号”），让待审/语义路径命中。
- AstrBot 的系统提示很长（约 4k 字），不要把暗号起成“记忆/上下文”这类常见词。
- 日志含私人原话，不要公开贴出；只贴 `attribution.py` 的汇总或打码片段。
