# 3–5 年稳定运行的存储与本地算力评估

> 口径：个人私聊、纯文本、单机、单用户；BGE-small（512 维）本地编码；可选大模型筛选器走远程 API。
> 数据来自本机实测：`dl_auto_source_vectors` 单条 512 维 JSON **7,911 B**、`dl_capture` 单条约 **270 B**、
> 5 个 tick 的 soak、5,000 条规模基准、真实 QQ 请求。

## 1. 每条消息占多少

| 组成 | 实测/估算 | 说明 |
|---|---|---|
| 原话 + 元数据 | ~0.27 KB | `dl_capture`（content/sha/time/state） |
| 字面索引 | ~1.3 KB | `dl_pending_terms`、`dl_auto_text_grams`、`text_index` |
| 语义向量（现状） | **7.9 KB** | 512 维 float 以 JSON 文本存（约 15.5 B/维） |
| 主题/分组/任务等 | ~0.8 KB | `dl_auto_topics/members/groups/jobs` |
| SQLite 页/WAL 摊销 | ~10–20% | 小库固定开销占比高，大库趋稳 |

- **标准口径：约 11 KB/条**（含向量 JSON）。
- 只做字面、不建语义：约 **2 KB/条**。
- 向量改存 float32 BLOB（512×4=2 KB）：约 **4.5 KB/条**（当前未实现，是最大的优化点）。

> 5,000 条基准库实测 31.2 MB（≈6.4 KB/条），因为该基准只建了部分向量；
> 生产环境后台会把每条都编码，所以按 11 KB/条做容量规划更安全。

## 2. 五年容量表（DB + 11 份备份）

备份策略按“7 日 + 4 周”轮转（峰值约 11 份完整库）。括号内为仅 1 份库。

| 消息量 | 5 年条数 | 标准 11 KB/条 | 优化 4.5 KB/条 | 仅字面 2 KB/条 |
|---|---|---|---|---|
| 50 条/天 | 91,250 | **~1.0 GB**（备份峰值 11 GB） | ~0.41 GB（4.5 GB） | ~0.18 GB（2 GB） |
| 100 条/天 | 182,500 | **~2.0 GB**（22 GB） | ~0.82 GB（9 GB） | ~0.37 GB（4 GB） |
| 200 条/天 | 365,000 | **~4.0 GB**（44 GB） | ~1.6 GB（18 GB） | ~0.73 GB（8 GB） |
| 300 条/天 | 547,500 | **~6.0 GB**（66 GB） | ~2.5 GB（27 GB） | ~1.1 GB（12 GB） |
| 1000 条/天 | 1,825,000 | **~20 GB**（220 GB） | ~8.2 GB（90 GB） | ~3.7 GB（40 GB） |

另加：

- **固定占用**：AstrBot + venv + 模型约 **2–3 GB**（实测 venv 1.44 GB、BGE 92 MB）。
- **AstrBot 自身会话历史**：约 0.5–1 KB/条，5 年再 +0.1–0.9 GB（按 200–1000 条/天）。
- **请求日志（可选）**：本 testbed 的 `llm_requests.jsonl` 每请求约 **12 KB**（含完整上下文）；
  200 条/天 ≈ **0.9 GB/年**。生产不需要保留全量请求日志，建议关闭或只留 7 天。
- **WAL**：通常 4–64 MB，崩溃后由 SQLite 恢复；定期 checkpoint 即可。

### 推荐磁盘

| 场景 | 建议可用空间 |
|---|---|
| ≤100 条/天 | **64 GB**（含系统与备份余量） |
| 200 条/天 | **128 GB** |
| 300–1000 条/天 | **256–512 GB**，同时启用向量 BLOB 优化 + 年度归档 |

## 3. 本地算力

| 项 | 实测 | 3–5 年建议 |
|---|---|---|
| 语义编码（BGE-small，512 维） | **3.3–3.7 ms/条**（4 线程） | 200 条/天 ≈ 0.7 s/天；1000 条/天 ≈ 3.7 s/天；积压 5,000 条约 12–20 s |
| 检索（`context_packet`） | M2 P50 23 ms / P95 34 ms | 单用户无压力 |
| 钩子端到端 | 真实 QQ P50 56 ms / P95 75 ms | 预算 1.5 s，余量充足 |
| 进程内存 | 5,000 条 + 模型 RSS **约 526 MB**；testbed 整体约 700 MB | **最低 4 GB，推荐 8 GB**（DB 页缓存 + 系统） |
| CPU | 4 线程编码；平时空闲 | **2 核最低，4 核推荐**（后台编码与回复并行） |
| GPU | 不需要（small 模型 CPU 足够） | 不建议为 BGE 上 GPU |
| 可选 LLM 筛选器 | 远程 API：+0.7 s、约 276 tokens/次 | 本地算力≈0；若改本地 7B 模型，需 **8–16 GB 显存**，不推荐 |

“模型失控”的算力风险不在本地：只要注入预算（450/600 字）和调用上限（≤10 次/会话/小时）生效，
CPU/RAM 不随对话时长增长；增长的是**存储**。

## 4. 3–5 年稳定运行的条件

1. **磁盘**：SSD，剩余空间 ≥ 表列值 + 20%；NFTS 单文件到 20 GB 没问题，但备份拷贝会变慢。
2. **备份轮转**：7 日 + 4 周（约 11 份）足够；不要无限保留。每季度做一次**恢复演练**。
3. **定期维护**：每月 `wal_checkpoint(TRUNCATE)`；每年 `VACUUM` 一次（需要临时 2× 空间）。
4. **归档**：超过 2–3 年的冷数据导出到独立库（保留原话与哈希），主库只留近期；插件当前无自动归档，需手工/脚本。
5. **监控阈值**：DB > 5 GB、WAL > 256 MB、备份失败、P95 钩子 > 1.5 s、恢复演练失败 → 处理。
6. **日志**：`llm_requests.jsonl` 只在测试环境保留；生产关闭或 7 天轮转，否则它会比记忆库还大。
7. **数据库健康**：SQLite `integrity_check` 每季度；异常断电后先检查再启动。

## 5. 结论

- **100–200 条/天、5 年**：标准实现约 **2–4 GB 数据 + 11 份备份 = 22–44 GB**；
  加系统/模型/日志，准备 **128 GB** 很宽裕。
- **算力**：4 核 / 8 GB 的单机足够；BGE-small 的编码与检索都不是瓶颈，
  真正的瓶颈是“每轮背景 + 可选 LLM 调用”的延迟，而不是 CPU/内存。
- **最大的优化杠杆**：把 512 维向量从 JSON 文本改成 float32 BLOB（7.9 KB → 2 KB），
  存储直接降到约 4.5 KB/条；其次是备份轮转与年度归档。
- 若消息量到 **1000 条/天**，标准方案 5 年要 ~20 GB 库 + 220 GB 备份，
  必须做向量 BLOB 优化或冷数据归档，否则备份窗口会明显变长。
