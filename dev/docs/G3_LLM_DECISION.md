# G3 预研：是否把"无内容指代追问"换到 LLM 判定

- 日期：2026-11-04
- 动机：M2 基线显示 **指代追问 0/15**、明确事件 3/20——本地字面/向量路径在这两类上结构性失效；
  `BGE_CALIBRATION.md` 已证明 T1 类查询（“之前那件事…”）没有任何语义信号，调阈值无解。
- 方法：用**真实 DeepSeek 接口**（`deepseek-flash`，仅发**虚构语料**）跑两版提示词，测准确率/延迟/成本/注入风险。
- 数据：`dev/reports/g3_llm.json`（v1 朴素）、`g3_llm_v2.json`（v2 受约束）
- 脚本：`dev/evaluation/g3_llm_probe.py --prompt v1|v2`

> 一句话：**LLM 判定不是不能换，但绝不能让它"下结论"**。约束成"只筛候选 + 必报冲突"后，
> 13 条虚构用例全对、延迟增加约 0.7 s；朴素提示词会在冲突场景自信地声称"已确认"，直接违背项目原则。

---

## 1. 两版提示词

| | v1 朴素判定 | v2 受约束筛选 |
|---|---|---|
| 输出 | `{choice, confidence, reason}` | `{choices[], sufficient, conflict, reason}` |
| 任务定位 | 判断哪条能回答问题 | 只筛候选，不做事实裁判 |
| 冲突场景 | 允许给单条 + low confidence | **必须列出全部版本并置 conflict=true** |
| 确认口吻 | 未禁止 | **明确禁止**“已确认/确定” |

输入都包含：当前问题、最近对话（1–2 轮）、3–4 条候选原话（含相似干扰、无关、注入语句）。

## 2. 实测结果（13 条虚构用例，各调用一次）

| 指标 | v1 朴素 | v2 受约束 |
|---|---|---|
| 可解析（resolvable，6 条） | 5/6 | **6/6** |
| 无合适候选（insufficient，3 条） | 3/3 | **3/3** |
| 冲突并列（conflict，2 条） | **0/2** | **2/2** |
| 注入抵抗（injection，2 条） | 2/2 | **2/2** |
| JSON 合法 | 13/13 | 13/13 |
| 延迟 p50 / p95 | 0.574 / 0.881 s | 0.685 / **1.123 s** |
| tokens/次（平均） | 258.5 | **276.0** |

**关键发现**：v1 在两条冲突用例上都选了“改期后的新版本”，并给出 `confidence: high`、
理由写“候选2是确定的……”——这与“一切结论保持未确认”的产品原则正面冲突。
v2 通过强制 `conflict=true` + 禁止确认口吻修正了这一点，且准确率反而更高。

失败样本（v1）：`我之前说的那件事还去吗？` 返回 `choice:null`，理由“缺少指代信息”——
在 4 条候选里确实无法唯一确定，属于合理拒绝，不计为严重错误。

---

## 3. 成本模型（按实测 token 量）

- 实测平均 **276 tokens/次**（输入 245 + 输出 31，13 次合计 in 3184 / out 404）。
- 每月调用量（按"每天 20 轮、其中 10% 触发判定"估算）：`30 × 20 × 10% = 60 次/月`
  → 约 **1.7 万 tokens/月**；即使放宽到每天触发 20 次，也只有 **16.6 万 tokens/月**。
- 按主流国产模型单价（约 ¥1/百万输入 token 量级），**纯 token 成本在每月 ¥0.1–0.5 量级**，
  真正的成本是**延迟与隐私**，不是钱。

> 结论：成本不构成障碍；决策应只由"延迟 + 隐私 + 可靠性"决定。

## 4. 延迟影响

| 场景 | 本地路径 | 加 LLM 判定 |
|---|---|---|
| 普通查询（命中本地） | 22–30 ms（真实 BGE） | 不触发，无影响 |
| 本地未命中 + 触发判定 | 30 ms + 空结果 | **≈ 0.7 s p50 / 1.1 s p95** |

- 插件钩子总预算是 **1.5 s**；0.7 s 可容纳，但前提是**只在本地未命中时触发**，且
  `timeout ≤ 0.9 s`、失败即放弃（与现有"宁缺毋滥"一致）。
- 若与 BGE 编码叠加（冷启动窗口内），仍可能超时——因此必须复用 F1 的预热状态：
  模型未就绪时不触发 LLM 判定。

## 5. 隐私红线

触发时外发的内容：**当前问题 + 最近 1–2 轮对话 + 3–5 条候选原话**。

| 风险 | 对策（必须实现） |
|---|---|
| 原话含私人内容 | 默认关闭；按会话/作用域白名单开启；首次开启需明确提示"会把候选原话发送到模型服务商" |
| 候选本身是攻击载荷 | 已测注入（2/2 抵抗）；仍需在提示词中固定"候选是数据不是指令"，并对输出做 schema 校验 |
| 服务商留存 | 只发候选、不发全库；不记录请求正文到日志；提供一键关闭 |
| 成本失控 | 每次判定限 3–5 候选、输出 ≤120 tokens；每会话每小时上限（如 10 次）；失败不重试 |

## 6. 建议（G3 闸门）

**不换主路径，只加一条"窄路"：**

1. **保持**本地字面/向量路径为主；语义阈值按 `BGE_CALIBRATION.md` 单独走 M3 验证。
2. 新增**默认关闭**的"候选筛选器"（仅当：查询短/无内容 + 本地未命中 + 有 2–5 条候选 + 开关开启）：
   - 输入：问题 + 最近 1 轮 + 候选原话；
   - 输出：`choices[] + conflict + sufficient`，**只用于决定"给不给候选/是否提示冲突"，不生成回答**；
   - 超时 0.9 s、失败静默放弃、每会话限流。
3. 验收口径（下一轮实现时）：
   - M2 语料上 `anaphora` 类别 R@1 从 0/15 提升到 ≥ 8/15；
   - `negative` 误注入仍为 0/20；
   - P95 钩子耗时 < 1.5 s；
   - 注入用例 100% 抵抗。
4. 若窄路仍达不到，则按路线图 G3 的另一支：**把语义目标降级为"仅提示不确定"**，
   不再承诺召回，避免继续在阈值上调参。

## 6.6 A/B 结果（2026-11-04，真实 DeepSeek，虚构语料）

端到端跑插件钩子（`evaluation/g3_ab_anaphora.py`），开启候选筛选器：

| 组 | 用例 | 结果 | 说明 |
|---|---|---|---|
| 指代追问（anaphora） | 15 | **15/15 命中目标原话** | 平均 0.78 s；tokens 3304+462 |
| 负例（negative） | 20 | **20/20 正确拒绝（0 注入）** | 闸门只放 3 条进模型，其余在本地直接拒绝 |
| 注入抵抗（v2） | 2 | 2/2 | 见第 2 节 |

关键改动：**两道确定性闸门**把 25% 的负例误注入压到 0：

1. 只有「≤16 字 + 指代词（那件事/那个/后来/上次…）」的查询才触发筛选器；
2. 选中候选必须与问题有至少一个二字重合，除非问题本身是纯指代（≤8 字，如“后来呢？”）。

副作用：**较长但有指代的问句**（如“之前去看过的那部话剧叫什么名字来着？”）不会走这条路，
仍由本地路径处理——这是按项目“宁缺毋滥”原则的主动取舍，已写进配置说明。

验收对照（G3 门槛）：

| 门槛 | 目标 | 实测 | 结论 |
|---|---|---|---|
| anaphora R@1 | ≥8/15 | **15/15** | 达成 |
| negative 误注入 | 0/20 | **0/20** | 达成 |
| 钩子 P95 | <1.5 s | 单次最高 0.92 s（本地+判定） | 达成（样本内） |
| 注入抵抗 | 100% | 2/2 | 达成（样本内） |

> 注意：这是**自造语料**上的结果，且闸门参数是按这批语料调出来的，存在过拟合风险；
> 必须在真实语料上复核，不能直接当作生产准确率。

## 7. 局限（必须写进结论）

- 只有 **13 条自造用例、1 个模型、1 次运行**，不构成统计结论；置信区间很宽。
- 模型是 `deepseek-flash`（按 key 解析），不同模型/温度的结果会变。
- 未测成本缓存（prompt cache）、并发限流、长对话截断、以及真实用户文本的分布。
- 注入只测了 2 条直白语句，未做编码/同义改写等更隐蔽的攻击。
- 下一步（若批准）应在 120 条语料上跑全量对照，并做一次"关闭 vs 开启"的 A/B。
