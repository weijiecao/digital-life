# 真实消息上的“有无大模型介入”检索准确率

- 日期：2026-11-05 / 2026-11-06
- 数据：`testbed` 真实采集库的只读副本；主 scope 21 条真实私聊（共 27 条、3 个 scope）
- 查询：
  - **40 个基础场景**：从真实消息内容人工构造的直接问法/追问/指代；
  - **40 个前缀探针**：每个基础场景加“你还记得吗？”前缀，共 **80 个正例探针**；
  - **10 个无信息负例**：询问真实消息里不存在的信息（猫、狗、车、生日等）。
- 对比：
  - **baseline**：`Store.context_packet`，本地字面/待审/背景，不调用 LLM；
  - **judge**：baseline 未命中目标时，用真实 DeepSeek 从候选里选；本地命中时不调用；
  - 多选时用 `filter_selection` 逐条过滤。
- 重复：3 轮。
- 证据：`dev/reports/real_messages_judge_eval_80_neg*.json`

> 隐私：本轮把 testbed 的测试用真实话术（候选原话/最近消息）发给 DeepSeek 做 judge；
> 生产开启必须显式同意，且只发候选与最近消息，不发全库。

---

## 1. 结果

| 指标 | baseline | 有 LLM 介入 |
|---|---|---|
| 80 个正例命中 | **27/80（33.75%）** | **70–71/80（87.5–88.75%）** |
| 40 个基础场景 | **14/40（35%）** | **34–35/40（85–87.5%）** |
| 本地未命中 | 53 条 | 53 条 |
| 其中找回 | — | **43–44/53** |
| judge 调用 | 0 | 53 次正例 + 10 次负例 |
| 平均耗时 | — | 0.80–0.85 s/次 |
| 正例 tokens | — | 约 14,194 prompt + 1,765 completion / 轮 |
| 负例误选 | — | **0/10** |

95% Wilson 区间：

- 71/80：**80.0%–94.0%**；70/80：**78.5%–93.1%**；
- 35/40：**73.9%–94.5%**；34/40：**70.9%–92.9%**；
- 负例 0/10 的“零误选”仍可能有约 26% 的上界（样本太小，不能当强保证）。

三轮：

| 轮 | 80 正例 baseline → judge | 40 基础 baseline → judge | 负例误选 |
|---|---|---|---|
| 1 | 27/80 → **71/80** | 14/40 → **35/40** | 0/10 |
| 2 | 27/80 → **70/80** | 14/40 → **35/40** | 0/10 |
| 3 | 27/80 → **71/80** | 14/40 → **35/40** | 0/10 |

## 2. 负例说明“信息不全”时模型没有硬编

10 个负例（猫、狗、日本、车、生日、电话、公司、大学、电影、昨天买什么）全部：

- judge 被调用；
- 模型没有选中任何候选；
- `negative_false_selections = 0/10`。

这说明：当用户信息确实不在库里时，当前提示词/候选筛选倾向于**拒绝选择**，而不是拿无关原话硬凑。
这是“信息不全”场景的正面证据。

---

## 3. 失败样本与归因

3 轮并集的失败集中在 5 组：

| id | 问题 | 归因 |
|---|---|---|
| `move_when` | 我什么时候搬家？ | 目标“下个月十五号”**在库里**，但候选只选到“搬家改到滨江区”，是候选覆盖/选择问题，不是信息缺失 |
| `pork_flavor` | 锅包肉是什么口味？ | 目标“巧克力锅包肉”**在库里**，候选覆盖/选择问题 |
| `later_mix` | 后来呢？ | 纯指代，没有具体所指；属于**问题信息不全/歧义** |
| `that_thing` | 那件事后来怎么样了？ | 同上，纯指代 |
| `that_thing_2` | 之前那件事呢？ | 同上，纯指代 |
| `tomorrow_drink`（偶发） | 明天喝什么？ | 多候选冲突，模型拒绝选择；信息在库里，但问题未限定 |

**结论**：

- 纯指代类失败（3 组）确实可以归为“用户问题信息不全”；
- `move_when`、`pork_flavor` 不能归为信息不全，是**候选覆盖/选择**仍有缺口；
- 80 个正例里 85–89% 的命中率已经比较稳定，但“85% 都是信息不全”这个解释只对一部分失败成立。

---

## 4. 数据量与独立性

- 80 个正例来自 **40 个基础场景 × 2 种问法**，基础场景又来自 **21 条真实消息**；
- 因此 80 不是 80 条独立真实用户问题，**40 个基础场景**更接近独立样本；
- 负例 10 条是人工构造的“无信息”查询，不是真实消息；
- 扩大探针量能观察问法稳定性，但不能替代更多真实聊天记录。

---

## 5. 边界

- 目标是“目标原话出现在 packet/选中原话里”，不是最终回复正确率；
- 没有真实用户的“不知道”标注；负例是人工定义的；
- 直接调 `Store.context_packet` + `judge_candidates`，不是完整 AstrBot 钩子；
  触发/限流由 `tests.test_model_judge` 覆盖；
- 模型请求名 `deepseek-chat`；正式评估要固定并记录实际返回模型；
- 真实测试话术已发给 DeepSeek 做 judge；生产需单独授权。

---

## 6. 建议

1. 若要把“85% 足够”作为结论，至少扩到 **100–200 个基础场景**，并来自更多真实聊天；
2. 纯指代失败可以通过“最近对话锚点 + 焦点事件”继续改善，但不应把“后来呢”当成可无限消解的查询；
3. `move_when`、`pork_flavor` 说明事件线候选要按**问题类型**补充：日期类取含日期来源，口味/属性类取属性来源；
4. 负例应保留在回归里，防止未来为了提高命中率而“硬选”；
5. 走完整插件钩子复核触发、限流、加载态。

**一句话：扩到 80 个正例 + 10 个负例后，LLM 介入把命中率从 27/80（33.75%）提升到 70–71/80（87.5–88.75%），负例 0/10 误选；纯指代失败可归为问题信息不全，但 `move_when`/`pork_flavor` 仍是候选覆盖问题，不能全部归因于用户信息不全。**
