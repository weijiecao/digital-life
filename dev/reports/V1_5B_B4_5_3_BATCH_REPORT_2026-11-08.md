# V1.5-B B4.5-3 批次边界回放报告

- 报告编号：DL-V1.5-B-REP-015
- 日期：2026-11-08
- 方法：固定 T1 trace 的 B2 结果，按真实 batch 边界重放 Resolver/Store
- 数据：Synthetic B4 v1（real_chat_records=0）
- 状态：**确定性批次边界压力测试完成；不是完整生产状态机**

## 1. 方法

使用同一条 T1 trace，按 `batch_size` 切分 scope 内消息：

- 每批消息的候选只能看到**上一批已提交**的事件；
- 本批新建事件在本批结束前不作为候选；
- B2 关系标签固定，不重新调用模型；
- 每个 batch 独立 `V15Store` 事务。

这隔离了批次边界/可见性，不包含模型随机性。

## 2. 结果

|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 8 | **1.00000** | **0.86667** | **0.92857** | 416 | 0 | 64 | 211 | 129 |
| 20 | 1.00000 | 0.34792 | 0.51623 | 167 | 0 | 313 | 119 | 221 |
| 40 | — | 0.00000 | 0.00000 | 0 | 0 | 480 | 0 | 340 |

## 3. 判读

- batch=8 与单条增量回放接近：F1 0.92857；
- batch=20 严重碎片化：F1 0.516；
- batch=40 **完全无法跨消息关联**：第一批没有已提交事件，340 条全部各自新建；
- source coverage 仍为 1.0，因为“全部新建”也算有归属；**高 coverage 掩盖了身份失败**；
- FP 始终 0，说明当前不是误合并，而是严重漏合并；
- 这是“批次结束才可见”的状态机；如果生产允许批内事件可见，结果会不同。

## 4. 结论

**批次边界会显著影响事件身份。**  
当前不能把 batch=8/20/40 当作同一质量；也不能用 coverage=1.0 证明可用。

## 5. 边界

- 不是完整状态机：没有 CLAIMED/lease/失败恢复/冷启动；
- 使用固定 B2 trace，不是重新调用模型；
- 事件可见性策略是“仅上一批已提交”；
- 合成数据；
- 不能据此判断真实 batch 策略。
