**判读：**

- 不是生产可用：覆盖率仍低，且评测是合成数据 + gold local context。

## 2. 回放方法

```text
B2 保存逐 query 的候选关系
  → 构造 JudgmentResult
  → B3 ConstrainedResolver
  → attach / defer / cannot-link
  → 统计 source 最终归属
```

初始化：

- 每个事件的第一条消息先 attach 到对应事件；
- 后续 2 条消息按 B2 预测回放；
- 不调用 LLM，不访问 V1 写接口。

指标：

- `attachment_precision = 正确归属 / 所有归属`
- `attachment_recall = 正确归属 / 所有 query`
- `false_merge_rate = 错误归属 / 所有 query`

## 3. 安全结论

B3 的 cannot-link 规则在本次回放中**没有被触发**（0 CONFLICT），因为 B2 没有把不同事件标成 SAME。  
真正起作用的是：

- `SAME_EVENT` 才 attach；
- `RELATED_CONTEXT` 只记录，不 attach；
- `DIFFERENT_EVENT` 建 cannot-link，不 attach。

因此 false merge 为 0，但代价是 26 个同事件对没有被归属。

## 4. 与 B2 的关系

| 阶段 | Precision | Recall | False merge |
|---|---:|---:|---:|
| B2 relation judge | 1.000 | 0.675 | 0 |
| B3.1 attachment replay | 1.000 | 0.675 | 0 |

B3 没有降低精度，也没有提升召回；它把 B2 的保守结果安全落成了归属决策。  
这说明当前瓶颈仍在 **关系判别 recall**，不是 Resolver 的合并策略。

## 6. 边界

- 合成留出集，不是真实语料；
- B2 使用 gold local context，生产不可得；
- 未测 batch=8/20/40 跨批次；
- 未测进程重启、删除后重建；
- 未测真实长程事件重现；
- 26 个未归属不能被当成“负例正确”；
- 不能对外宣称“事件记忆可用”。
