**判读：**

- 模型在“给定正确候选”时**没有把不同事件标成 SAME**，precision 1.0；
- 但 80 个同事件对中只认出 54 个，**26 个被保守标成 RELATED_CONTEXT**；
- 这是“高精度、低召回”的关系判别器，不能直接用于自动归属；
- 需要 B3 约束归属/拒判，或改进判别上下文，不能靠放宽阈值硬合并。

## 2. 实验设置

### 2.1 Gold 候选隔离

每个 query 消息的候选集固定为同 scope 的 4 个事件锚点：

- 1 个 gold 事件；
- 3 个其他事件；
- 其中包含“同目的地不同月份”的困难负例。

模型只判断关系，不检索、不写库。

### 2.2 上下文

为了让“酒店/预算”这类补充句能与首条计划关联，实验提供了**同事件的前缀原话**作为局部上下文：

```text
source: 当前原话
context: 同一事件中早于当前原话的消息
candidates: 4 个事件锚点
```

**注意：这是 gold local context，属于隔离实验条件，不是生产可用上下文。**  
生产环境只能使用检索到的上下文，因此该 recall 不应直接外推到线上。

### 2.3 输出契约

```json
{
  "schema_version": "v1.5b.1",
  "relations": [
    {"candidate_event_id": "evt_a", "label": "SAME_EVENT", "reason_codes": ["..."]}
  ],
  "suggested_action": "ATTACH_EXISTING",
  "target_event_id": "evt_a"
}
```

确定性校验：

- 必须覆盖所有候选；
- 不得出现未提供的 candidate ID；
- label 必须是 `SAME_EVENT / DIFFERENT_EVENT / RELATED_CONTEXT / UNCERTAIN`；
- 缺失、重复、非法 ID 都记为 invalid；
- 模型输出不直接写库。

同一 prompt / 数据 / 模型，重复 3 次：

| 运行 | SAME | RELATED | Recall | F1 | Precision |
|---|---:|---:|---:|---:|---:|

这确认了结论：模型稳定地“不误合并”，但也稳定地“不敢确认”约三分之一同事件对。

## 4. 错误分析

26 个 FN 全部不是“标成 DIFFERENT”，而是“标成 RELATED_CONTEXT”。  
这说明模型倾向于：

- 认出“有关”；
- 但不敢确认“同一具体事件”；
- 特别是酒店、预算、排队、坚持天数等**补充细节**。

这不是 false merge；恰好相反，是**过度保守**。  
如果直接把 RELATED 当 SAME，会引入误合并；如果直接丢弃，会损失 32.5% 的同事件对。

## 7. 边界与风险

- 只用合成留出集，不是真实语料；
- 使用 **gold local context**，生产不可得；
- 单模型、三次重复，未测其他模型；
- 没有 B3 约束归属，不能把 54 个 SAME 直接落库；
- `RELATED_CONTEXT` 不能作为合并依据；
- 没有测试真实删除、跨 scope、长程事件重现；
- 不能对外宣称“事件关系判别可用”。

## 8. 下一步：B3

B3 应做：

1. 把 `SAME_EVENT` 只当 proposal；
2. 加入 cannot-link / 事件锚点冲突检查；
3. 对 `RELATED_CONTEXT` 保留但不合并；
4. 评估“只在高置信时合并”的 precision/recall 曲线；
5. 用真实评测量化：宁可少合并，也不能把不同事件串起来。

目标不是把 recall 硬拉到 1.0，而是：

```text
false merge ≤5%
同时尽量保留可确认的 SAME_EVENT
```
